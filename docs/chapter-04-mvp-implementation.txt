
ГЛАВА 4. РЕАЛИЗАЦИЯ MVP

В данной главе описывается практическая реализация минимально жизнеспособного продукта (MVP) платформы Wellbeing Monitor: выбор технологического стека, реализация ключевых модулей и перечень функций, доступных конечным пользователям на момент завершения курсового проекта. Реализация ориентирована на удалённые команды и сценарий «ежедневный сбор самочувствия + аналитика для HR и руководителей + сопоставление с метриками задач из трекеров».


4.1. Выбор технологий

При проектировании MVP приоритетом являлись скорость разработки, предсказуемость развёртывания, изоляция данных компаний (multi-tenant) и возможность последующего наращивания функциональности без полной перестройки архитектуры. Стек выбран монолитным на стороне сервера с отдельным лёгким клиентом сбора данных.


Frontend

Для веб-интерфейса администратора и HR не разрабатывалось отдельное одностраничное приложение (SPA). В качестве frontend-части дашборда используется серверный рендеринг на шаблонах Blade (фреймворк Laravel), стилизация — Tailwind CSS, сборка фронтенд-ресурсов — Vite. Графики на главной панели и в разделах аналитики строятся с помощью библиотеки Chart.js.

Такой подход обоснован для MVP следующими соображениями. Во-первых, дашборд и API развёртываются единым артефактом (один контейнер PHP-FPM), что упрощает сопровождение в учебной и пилотной среде. Во-вторых, для курсового проекта достаточно форм входа, таблиц, фильтров по периоду и кнопок запуска анализа без сложной клиентской маршрутизации. В-третьих, при необходимости масштабирования REST API v1 уже выделен и может обслуживать отдельный SPA без изменения доменной логики.

Для сотрудников, проходящих микроопрос, реализовано браузерное расширение Google Chrome (Manifest V3) на чистом JavaScript (ES-модули) без этапа сборки webpack. Расширение содержит popup для ответов на вопросы, страницу настроек (URL API, секретный ключ компании, идентификатор сотрудника) и фоновый service worker для напоминаний. Выбор MV3 и «лёгкого» JS соответствует ограничениям popup и требованию минимального порога установки для пилота.


Backend

Серверная часть реализована на PHP 8.3 и Laravel 12. Laravel выбран как зрелая экосистема с встроенной аутентификацией, миграциями, очередями, валидацией и ORM (Eloquent), что сокращает объём инфраструктурного кода.

Архитектура приложения организована по слоям:
— HTTP-контроллеры (Dashboard и API v1);
— сервисы предметной области (CheckInService, AnalyticsService, BurnoutRiskService, LlmAnalysisService, DeepAnalysisExportService и др.);
— репозитории для доступа к данным (паттерн Repository);
— DTO и перечисления (enum) для типизации входных данных;
— фоновые задачи (Jobs) и планировщик (scheduler).

Аутентификация пользователей дашборда выполняется через Laravel Sanctum (сессии для веб-интерфейса). Доступ расширения к API — по секретному ключу компании (secret_key, 48 символов), передаваемому в запросе check-in; отдельный OAuth для сотрудников в MVP не предусмотрен.

Развёртывание выполняется в Docker Compose: контейнеры nginx (обратный прокси), PHP-FPM (приложение), PostgreSQL 16, Redis, воркер очереди и планировщик. Порт веб-доступа по умолчанию — 8080.


База данных

Основное хранилище — реляционная СУБД PostgreSQL 16. Выбор PostgreSQL обусловлен надёжной поддержкой транзакций, внешних ключей, индексов по датам и полям компании, а также типа JSON для хранения снимков метрик задач.

Структура данных включает:
— ядро wellbeing: companies, users, company_user (связь пользователь–компания с ролью), departments, employees, surveys, survey_questions, survey_answers;
— интеграции: integration_providers, company_integrations (учётные данные шифруются), employee_integration_identities, work_progress_snapshots.

Redis используется не как основное хранилище, а как инфраструктурный компонент: кэш агрегатов аналитики (TTL порядка 5 минут), драйвер сессий и брокер очередей для асинхронной обработки после check-in.


Средства анализа данных

В MVP применяется комбинация детерминированных правил и внешней большой языковой модели (LLM).

Детерминированный анализ:
— агрегация ответов SQL-запросами через слой репозиториев (средние значения, тренды по дням, сводки по отделам и сотрудникам);
— расчёт числового score для ответов со шкалой (AnswerScoreCalculator);
— оценка риска выгорания по порогам среднего настроения и динамике за две недели (BurnoutRiskService).

Интеллектуальный анализ:
— формирование рекомендаций через HTTP API, совместимый с OpenAI Chat Completions (в проекте используется провайдер Google Gemini через OPENAI_BASE_URL);
— сервис LlmAnalysisService отправляет системный промпт роли и JSON с агрегированными данными, получает текст рекомендаций на русском языке.

Для глубокого анализа перед отправкой в LLM JSON сжимается (матрица employee_delivery_matrix, сводки wellbeing и KPI без сырых массивов check-in), что снижает объём запроса и повышает устойчивость к ограничениям API.

Отдельный контур классического NLP (модели тональности на базе машинного обучения в Python) в MVP не развёртывался; анализ «эмоционального состояния» опирается на шкальные метрики, правила риска и интерпретацию LLM.


4.2. Реализация сбора эмоциональных сигналов

Сбор данных реализован по схеме «расширение — REST API — сервис — база данных».

На стороне клиента сотрудник один раз настраивает адрес сервера, secret_key компании и свой external_id (например proj-001). При открытии popup расширение запрашивает список активных вопросов опроса (GET /api/v1/extension/survey-questions). Пользователь заполняет форму: настроение и стресс (шкала 1–5), поддержка команды (да/нет), при желании — текстовый комментарий.

Отправка ответов выполняется методом POST /api/v1/extension/check-in. В теле запроса передаются secret_key, данные сотрудника (external_id, опционально email, имя, внешний id отдела) и массив answers с идентификаторами вопросов.

На сервере CheckInService выполняет:
1) проверку secret_key и определение компании;
2) создание или обновление записи сотрудника (upsert по паре company_id + external_id);
3) валидацию того, что все question_id относятся к активному опросу компании;
4) сохранение ответов в survey_answers с полями answer, score (для шкал), check_in_date (текущая календарная дата);
5) постановку в очередь задачи ProcessCheckInAnalyticsJob для последующей обработки.

Ограничение «один check-in в день» обеспечивается привязкой к check_in_date; повторная отправка в тот же день перезаписывает или дополняет ответы в рамках бизнес-логики репозитория (в зависимости от реализации storeAnswers).

Демонстрационные данные для тестирования формируются сидером DatabaseSeeder (компании Acme и project, сотрудники, месяц ответов с вариативными значениями настроения и стресса).


4.3. Реализация анализа тональности

В терминах курсового проекта под «анализом эмоционального состояния» в MVP понимается совокупность количественной обработки сигналов и качественной интерпретации, а не отдельный модуль sentiment analysis на базе классификатора текста.

Количественный анализ реализован полностью:
— ответы типа scale преобразуются в числовой score;
— AnalyticsService вычисляет average_mood_score, тренды moodTrendByDate, сводки по отделам и сотрудникам;
— для каждого сотрудника в глубоком анализе DeepAnalysisEmployeeMatrixBuilder формирует показатели avg_mood, avg_stress, team_support_yes_rate за выбранный период.

Текстовые комментарии (четвёртый вопрос опроса) сохраняются в поле answer. Автоматическая разметка тональности (positive/negative/neutral) с помощью отдельной NLP-модели в текущей версии не реализована. Комментарии доступны при полном экспорте ответов для дашборда и могут учитываться большой языковой моделью при базовом анализе wellbeing, куда передаётся развёрнутый JSON с check_ins.

Таким образом, раздел 4.3 в рамках MVP следует трактовать как реализацию анализа эмоциональных показателей по шкалам и трендам; полноценный подмодуль тональности текста запланирован как направление развития после MVP.


4.4. Реализация интеграции KPI

Интеграция производственных показателей (KPI delivery) реализована через подсистему коннекторов к системам учёта задач.

Архитектура интеграций:
— справочник integration_providers (Jira Cloud, Linear, GitHub Issues, Яндекс Трекер);
— запись company_integrations на компанию с зашифрованными credentials и статусом подключения;
— опциональный явный маппинг employee_integration_identities;
— снимок work_progress_snapshots на период [period_from, period_to] с JSON payload.

Паттерн коннектора: интерфейс WorkTrackerConnector, реестр IntegrationRegistry, оркестрация IntegrationManager::syncWorkProgress. Для Jira Cloud реализован JiraCloudConnector: аутентификация Basic (email + API token), поиск задач POST /rest/api/3/search/jql, пагинация nextPageToken, агрегация метрик по assignee (создано, закрыто, просрочено, открыто на конец периода, ключи просроченных задач, среднее время решения).

Связь пользователя трекера с сотрудником платформы выполняется по точному совпадению email (IntegrationEmployeeMatcher), если Jira отдаёт emailAddress в данных assignee; иначе assignee попадает в список unmapped_assignees с предупреждением в интерфейсе.

После синхронизации WorkProgressAggregator объединяет снимки нескольких провайдеров, мержит метрики одного сотрудника (ProviderMetricsMerger) и подготавливает структуру work_progress для дашборда и глубокого анализа.

Пользовательский сценарий: страница «Интеграции» — ввод учётных данных, тест соединения; страница «Глубокий анализ» — выбор периода и провайдеров, кнопка «Синхронизировать трекеры», просмотр данных трекера и preview JSON.


4.5. Реализация механизма выявления риск-паттернов

Выявление рисков в MVP реализовано в двух взаимодополняющих формах: автоматические пороговые правила (без LLM) и сопоставление wellbeing с KPI в матрице для экспертного анализа и LLM.

4.5.1. Пороговая модель риска выгорания

Класс BurnoutRiskLevel (low, medium, high) и сервис BurnoutRiskService оценивают риск по среднему баллу настроения за последние 7 дней и сравнению с предыдущими 7 днями:
— при среднем настроении ниже 2,5 — уровень high;
— при среднем ниже 3,0 — medium;
— при среднем ниже 3,5 и падении относительно прошлой недели не менее чем на 0,3 — medium;
— иначе — low.

Дополнительно вычисляется тренд: improving, declining или stable (порог изменения 0,2 балла). Результат отображается на главном дашборде в блоке аналитики.

4.5.2. Паттерны «нагрузка + самочувствие»

DeepAnalysisEmployeeMatrixBuilder формирует для каждого сотрудника единую строку: wellbeing-агрегаты и tasks-метрики. Типовые паттерны, которые система делает видимыми для HR и PM:
— высокий overdue_count при низком avg_mood;
— рост tasks_created при высоком avg_stress;
— отсутствие маппинга Jira (tasks есть, wellbeing по сотруднику в системе не связывается).

Формальная библиотека исторических сценариев с коэффициентом сходства в базе данных в MVP не хранится; сравнение с «эталонными» ситуациями возлагается на LLM в рамках промптов глубокого анализа при наличии цифр в матрице.


4.6. Реализация рекомендательной системы

Рекомендательная подсистема построена на генеративной модели (LLM-as-a-recommender), а не на жёстком дереве правил IF-THEN.

Компоненты:
— LlmAnalysisService — HTTP-клиент к /chat/completions, нормализация ответа (нумерованный список на русском, удаление markdown);
— каталоги промптов config/analysis_prompts.php (роли: психолог, HR-аналитик, руководитель) и config/deep_analysis_prompts.php (product owner, HR+delivery, team lead);
— ограничения формата в config/llm.php (запрет выдуманных метрик, требование цифр и имён для глубокого анализа).

Сценарий базового анализа (/dashboard/analysis): экспорт ответов за период (EmployeeResponsesExportService), выбор промпта, POST recommend — возврат текста рекомендаций без сохранения в БД.

Сценарий глубокого анализа (/dashboard/deep-analysis): сбор wellbeing + синхронизация трекеров, построение матрицы, сжатие JSON (DeepAnalysisLlmPayloadBuilder), вызов analyzeCombined. Опционально sync_first в теле запроса выполняет синхронизацию непосредственно перед рекомендацией.

Ограничение частоты: throttle 10 запросов в минуту на эндпоинты recommend. При ошибках провайдера (например HTTP 503 при перегрузке модели) пользователю отображается сообщение об ошибке LLM API; повторная попытка — вручную.

Перспектива: сохранение истории рекомендаций, явная приоритизация пунктов (critical/high/medium), кэширование ответов на идентичный период.


4.7. Реализация панели мониторинга

Веб-панель реализована как набор страниц Laravel Blade с общей навигацией.

Основные экраны:
— /welcome, /onboarding — приветствие и создание компании, выдача secret_key;
— /login, /register — аутентификация HR и администраторов;
— /companies — выбор активной компании (multi-company через company_user);
— /dashboard — обзор: среднее настроение, уровень риска выгорания, график тренда, сводка по отделам, список сотрудников;
— /dashboard/employees/{id} — история check-in конкретного сотрудника;
— /dashboard/analysis — выбор периода, экспорт JSON, получение LLM-рекомендаций по wellbeing;
— /dashboard/integrations — подключение Jira и других трекеров, тест, удаление интеграции;
— /dashboard/deep-analysis — синхронизация KPI, просмотр данных трекера, preview JSON для LLM (сжатый и полный режим), получение рекомендаций с учётом задач.

Фильтрация аналитики выполняется по датам «с — по», с пресетами 7/14/30 дней на страницах анализа. Данные для графиков загружаются через внутренние API-методы контроллеров и сервис аналитики с кэшированием в Redis.

Ролевая модель: admin, hr, manager (поле role в связи пользователь–компания). Middleware EnsureUserHasCompany ограничивает доступ к дашборду наличием выбранной компании.


4.8. Основные функции MVP

Ниже приведён перечень реализованного функционала, сгруппированный по ролям.

Для сотрудника (браузерное расширение):
— установка и настройка подключения к серверу компании;
— получение списка вопросов ежедневного опроса;
— отправка check-in (шкалы, да/нет, текстовый комментарий);
— автоматическое создание профиля сотрудника при первом ответе.

Для HR / администратора (веб-дашборд):
— регистрация и создание компании, получение secret_key для расширения;
— просмотр агрегированной аналитики wellbeing за период;
— просмотр риска выгорания (low/medium/high) и тренда настроения;
— детализация по сотруднику и отделу;
— экспорт ответов в JSON;
— получение рекомендаций LLM по трём сценариям (психолог, HR, руководитель);
— подключение интеграций с трекерами задач (Jira Cloud и др.);
— синхронизация метрик задач за выбранный период;
— глубокий анализ: матрица «сотрудник × wellbeing × KPI», preview данных для LLM, рекомендации с привязкой к цифрам и ключам просроченных задач;
— предупреждения о немаппленных пользователях Jira и об ошибках интеграции.

Для разработчика / сопровождения:
— развёртывание через Docker Compose (make setup);
— демо-данные через DatabaseSeeder;
— REST API v1 для расширения;
— фоновые очереди Redis для обработки check-in;
— шифрование учётных данных интеграций в БД.

Функции, сознательно не вошедшие в MVP (ограничения):
— отдельный NLP-модуль тональности комментариев;
— персистентное хранение риск-профилей и рекомендаций в БД;
— OAuth для dashboard и whitelisted Jira app для API email;
— производственные метрики вне трекеров задач (CI/CD, инциденты);
— полноценная тарификация и жёсткое enforcement лимитов LLM (заготовки PlanLimitService без полной продуктовой обвязки);
— мобильное приложение и SSO.

Заключение по главе

MVP платформы Wellbeing Monitor реализует сквозной цикл: сбор эмоциональных сигналов через расширение, хранение и агрегация в PostgreSQL, визуализация и пороговая оценка риска на дашборде, интеграция KPI из Jira-подобных систем, формирование сводной матрицы и генерация рекомендаций с помощью LLM. Выбранный стек (Laravel, PostgreSQL, Redis, Docker, Chrome MV3, Gemini/OpenAI-compatible API) обеспечивает баланс между трудоёмкостью курсовой реализации и демонстрируемой ценностью для HR удалённых команд. Дальнейшее развитие проекта логично направить на модуль тональности текста, сохранение истории рисков и рекомендаций, а также устойчивость LLM-контура (повторы запросов, очередь генерации).
