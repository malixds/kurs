# Wellbeing Monitor — обзор системы для бизнес-аналитика

Документ описывает платформу **простым языком**: зачем она нужна, кто ею пользуется, какие данные собираются и как они доходят до отчётов и рекомендаций.

> Техническая версия с деталями реализации: [architecture-end-to-end.md](./architecture-end-to-end.md)

---

## 1. Зачем нужна система

**Wellbeing Monitor** помогает компаниям с удалёнными командами:

- **ежедневно** узнавать, как себя чувствуют сотрудники (настроение, стресс, поддержка команды);
- **видеть тренды** на дашборде для HR и руководителей;
- **получать рекомендации** от ИИ на основе собранных данных;
- **сопоставлять самочувствие с рабочей нагрузкой** (задачи из Jira, Linear и др.) — функция «глубокого анализа».

**Проблема, которую решает продукт:** руководители и HR не видят ранние сигналы выгорания и перегрузки, пока не случится текучесть или срыв сроков.

---

## 2. Кто пользуется системой

| Роль | Как заходит | Что делает |
|------|-------------|------------|
| **Сотрудник** | Браузерное расширение Chrome | Раз в день проходит короткий опрос (1–2 минуты) |
| **HR / Admin / Manager** | Веб-сайт (дашборд) | Смотрит аналитику, запрашивает рекомендации ИИ, настраивает интеграции |
| **Новая компания** | Регистрация на сайте | Создаёт компанию, получает ключ для расширения |

**Важно:** сотрудник **не логинится** на сайт — он только заполняет опрос в расширении. HR и руководители работают в веб-дашборде под своим логином.

---

## 3. Из чего состоит система (простыми словами)

```
┌─────────────────┐
│  Расширение     │  ← сотрудник отвечает на вопросы
│  в браузере     │
└────────┬────────┘
         │ отправка ответов
         ▼
┌─────────────────┐
│  Сервер         │  ← хранит данные, считает метрики,
│  (платформа)    │    подключается к Jira и др.
└────────┬────────┘
         │
         ▼
┌─────────────────┐
│  Дашборд        │  ← HR и руководители смотрят отчёты
│  (веб-сайт)     │    и получают рекомендации ИИ
└─────────────────┘
```

Три части:

1. **Расширение** — точка сбора данных от сотрудников.
2. **Сервер** — «мозг»: база данных, расчёты, интеграции, ИИ.
3. **Дашборд** — интерфейс для HR и руководителей.

---

## 4. Как собираются данные wellbeing

### Шаг 1. Настройка (один раз)

HR или IT:
1. Создаёт компанию в системе (или использует демо).
2. Получает **секретный ключ компании** (48 символов).
3. Раздаёт сотрудникам инструкцию: установить расширение, вставить ключ и свой ID (например `emp-001`).

### Шаг 2. Ежедневный опрос

Сотрудник открывает расширение и отвечает на 4 вопроса:

| № | Тема | Формат ответа |
|---|------|---------------|
| 1 | Общее настроение | Шкала 1–5 |
| 2 | Уровень стресса | Шкала 1–5 |
| 3 | Чувствовал ли поддержку команды | Да / Нет |
| 4 | Комментарий (необязательно) | Свободный текст |

### Шаг 3. Сохранение

Ответы уходят на сервер и привязываются к:
- **компании** (по секретному ключу);
- **сотруднику** (по его ID, например `emp-001`);
- **дате** (один check-in = один календарный день).

Если сотрудник новый — система **создаёт его автоматически** при первом ответе.

### Что НЕ собирается через расширение

- Данные с экрана, переписки, сайтов
- Медицинские диагнозы
- Геолокация
- Личный кабинет сотрудника на платформе

## 5. Где хранятся данные

Все данные компании хранятся **централизованно на сервере** в базе данных.

**Основные сущности:**

| Сущность | Что это | Пример |
|----------|---------|--------|
| **Компания** | Организация-клиент | Acme Remote Corp |
| **Сотрудник** | Участник опроса | Alice, ID `emp-001` |
| **Отдел** | Группа внутри компании | Engineering, HR |
| **Ответ на опрос** | Одна реплика на один вопрос в один день | «Настроение: 4», дата 29.05.2026 |
| **Опрос** | Набор вопросов | «Daily Wellbeing Check-in» |

**Изоляция:** данные одной компании **не видны** другой. HR видит только свою компанию (или несколько, если у него есть доступ).

---

## 6. Что видит HR на дашборде

### 6.1. Обзор команды (`/dashboard`)

- **Средний уровень настроения** за выбранный период
- **Риск выгорания** (низкий / средний / высокий) — на основе динамики за последние недели
- **График** изменения настроения по дням
- **Сравнение отделов**
- **Таблица сотрудников** с количеством ответов и средним баллом

### 6.2. Карточка сотрудника

- История check-in по дням
- Ответы на каждый вопрос
- Индивидуальный риск выгорания

### 6.3. Анализ с ИИ (`/dashboard/analysis`)

HR выбирает:
- **период** (например, последние 7 дней);
- **роль аналитика** (психолог / HR-аналитик / бизнес-консультант).

Система отправляет собранные ответы в **языковую модель (ИИ)** и возвращает **список рекомендаций** — что делать руководителю и HR. Без лишних вступлений, только действия.

**На вход ИИ:** только данные опросов за период (настроение, стресс, комментарии).  
**На выход:** 3–6 конкретных рекомендаций на русском.

## 7. Интеграции с task trackers (рабочие задачи)

Помимо опросов wellbeing, система умеет **подтягивать данные о задачах** из внешних систем.

### Поддерживаемые системы

| Система | Что можно получить |
|---------|-------------------|
| Jira Cloud | Закрытые/открытые задачи, просрочки, нагрузка по людям |
| Linear | То же |
| GitHub Issues | То же |
| Яндекс Трекер | То же |

### Как это работает

1. HR **подключает** интеграцию на странице «Интеграции» (вводит API-ключ / токен).
2. На странице «Глубокий анализ» нажимает **«Синхронизировать»** за выбранный период.
3. Система **скачивает снимок** метрик задач и сохраняет его.
4. Система **сопоставляет** людей из трекера с сотрудниками wellbeing (по email или ручному маппингу).

### Какие метрики задач доступны

**По команде:**
- сколько задач закрыто;
- сколько просрочено;
- сколько открыто;
- сколько человек участвовало.

**По сотруднику:**
- закрыто / создано / обновлено задач;
- просрочки;
- открытые задачи на конец периода.

## 8. Глубокий анализ (wellbeing + задачи)

Это **ключевая функция для связки «самочувствие ↔ нагрузка»**.

```
Данные опросов          +          Данные из Jira/Linear/...
       │                                    │
       └──────────────┬─────────────────────┘
                      ▼
              Объединённый отчёт
                      │
                      ▼
                 ИИ-рекомендации
         (с учётом и mood, и задач)
```

HR выбирает период, подключённые интеграции и сценарий (например, «владелец продукта» или «тимлид»). ИИ получает **оба блока данных** и даёт рекомендации вроде:

- у кого одновременно высокий стресс и много просрочек;
- кому нужна поддержка на 1:1;
- где риск срыва релиза из-за перегрузки.

**Важно для планирования:** именно здесь сейчас **сходятся** wellbeing и рабочие метрики. Отдельного блока «производственные метрики» (CI/CD, инциденты, деплои) **пока нет**.

## 10. Что есть сейчас и чего нет

### ✅ Реализовано

| Возможность | Статус |
|-------------|--------|
| Ежедневный опрос через расширение | Работает |
| Дашборд с графиками и риском выгорания | Работает |
| Несколько компаний у одного пользователя | Работает |
| ИИ-рекомендации по wellbeing | Работает |
| Интеграции с Jira, Linear, GitHub, Яндекс Трекер | Работает |
| Глубокий анализ (wellbeing + задачи) | Работает |
| Регистрация новых компаний | Работает |

### ❌ Не реализовано / в планах

| Возможность | Комментарий |
|-------------|-------------|
| **Производственные метрики** (деплои, CI/CD, инциденты, uptime) | Нет провайдеров и UI |
| SSO / корпоративный вход | Только email + пароль |
| Мобильное приложение | Только Chrome-расширение |
| Автоматические алерты HR | Нет push/email при критическом падении mood |
| Лимиты на ИИ-запросы | Заданы в конфиге, но не enforced |
| Медицинские заключения / диагнозы | Продукт не ставит диагнозы, только агрегаты |

## 11. Границы проекта — для планирования интеграций

Если нужно добавить **производственные метрики** (не задачи, а именно production: деплои, инциденты, SLA), важно понимать:

### Где данные «живут» сейчас

| Тип данных | Откуда берётся | Где хранится | Где используется |
|------------|----------------|--------------|------------------|
| Wellbeing (опросы) | Расширение | База: ответы сотрудников | Дашборд, Analysis, Deep Analysis |
| Task metrics | Jira, Linear, GitHub, Yandex | База: снимки за период | Только Deep Analysis |
| ИИ-рекомендации | Gemini API | Не хранятся (генерируются on-demand) | Экран Analysis / Deep Analysis |

### Куда логично «встроить» production metrics

**Рекомендуемая точка:** туда же, куда сейчас попадают метрики задач — в **«Глубокий анализ»**, как третий блок данных рядом с wellbeing и task metrics.

**Что потребуется спроектировать:**

1. **Источники** — откуда брать метрики (Grafana, GitLab CI, Datadog, внутренний API)?
2. **Периодичность** — по запросу HR (как сейчас Jira) или автоматически?
3. **Уровень детализации** — по команде, по человеку или только агрегат?
4. **Связь с сотрудниками** — нужен ли маппинг (как email в Jira) или достаточно team-level?
5. **Презентация в ИИ** — какие поля передавать модели для корреляции с mood?

### Что можно переиспользовать без переделки продукта

- Механизм «подключить внешнюю систему → синхронизировать за период → сохранить снимок»
- Маппинг сотрудников (email / external ID)
- Страница Deep Analysis как место, где HR видит **объединённую** картину
- ИИ-сценарии (можно добавить новые роли аналитика)

## 12. Бизнес-правила и ограничения

| Правило | Описание |
|---------|----------|
| Один check-in = один день | Дата фиксируется сервером в момент отправки |
| Компания изолирована | HR не видит чужие данные |
| Секретный ключ = доступ для расширения | Кто знает ключ — может отправлять ответы от имени компании |
| ИИ не диагностирует | Только рекомендации для HR, без медицинских формулировок |
| Task sync — по запросу | Данные из Jira не обновляются сами, HR нажимает «Синхронизировать» |
| Кэш аналитики | Обзор на дашборде обновляется с задержкой до 5 минут |

## 14. Глоссарий

| Термин | Значение |
|--------|----------|
| **Check-in** | Однократное прохождение опроса сотрудником за день |
| **Wellbeing** | Показатели самочувствия из опроса (настроение, стресс и т.д.) |
| **Secret key** | Секретный ключ компании для расширения (48 символов) |
| **External ID** | Уникальный ID сотрудника в системе клиента (`emp-001`) |
| **Snapshot** | Сохранённый снимок метрик из внешней системы за период |
| **Deep Analysis** | Анализ, объединяющий wellbeing и метрики задач |
| **Analysis** | ИИ-анализ только по данным опросов |
| **Burnout risk** | Оценка риска выгорания (низкий / средний / высокий) по динамике mood |

---

## 15. Резюме для планирования

1. **Ядро продукта** — ежедневный опрос через расширение + дашборд для HR.
2. **Данные wellbeing** — уже полный цикл: сбор → хранение → отчёты → ИИ.
3. **Данные о задачах** — подключены через Jira/Linear/GitHub/Yandex, используются в Deep Analysis.
4. **Production metrics** — **не входят** в текущий scope; архитектурно ближе всего к блоку интеграций и Deep Analysis.
5. **Точка расширения** — добавить новые источники данных и включить их в объединённый отчёт для ИИ, не меняя логику сбора wellbeing.

Если нужны уточнения по конкретному процессу или данным — можно опираться на технический документ [architecture-end-to-end.md](./architecture-end-to-end.md) или задать вопрос команде разработки.
