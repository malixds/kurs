
ГЛАВА 3. ПРОЕКТИРОВАНИЕ СИСТЕМЫ

В данной главе рассматриваются проектные решения платформы Wellbeing Monitor — системы мониторинга психологического состояния удалённых сотрудников с интеграцией метрик выполнения задач (KPI delivery) и формированием рекомендаций на основе большой языковой модели (LLM). Описание согласовано с архитектурой реализуемого MVP (Laravel 12, PostgreSQL, Redis, браузерное расширение Chrome, интеграции с Jira Cloud, Linear, GitHub Issues, Яндекс Трекер). Элементы, не вошедшие в текущую версию продукта, обозначены как направления развития.


3.1. Концепция сбора эмоциональных данных

3.1.1. Назначение

Система предназначена для регулярного получения сигналов о самочувствии сотрудников без проведения длительных опросов и без сбора данных с рабочего экрана, переписки или сторонних приложений. Проектная цель — обеспечить раннее выявление стресса, снижения вовлечённости и риска профессионального выгорания на уровне отдельного человека, подразделения и организации в целом.

3.1.2. Микроопросы (check-in)

Основной канал сбора эмоциональных данных — ежедневный микроопрос, проходимый через браузерное расширение Google Chrome (Manifest V3). Состав опроса «Daily Wellbeing Check-in»:

  1) общее настроение — количественный сигнал, шкала от 1 до 5;
  2) уровень стресса — количественный сигнал, шкала от 1 до 5;
  3) ощущение поддержки команды — качественный (бинарный) сигнал, ответ «да» или «нет»;
  4) комментарий — текстовый сигнал, необязательное поле свободного ввода.

Принципы организации сбора:

— короткий цикл заполнения (ориентировочно 1–2 минуты), один check-in на календарный день на одного сотрудника;

— идентификация без личного кабинета на портале: используется секретный ключ компании (secret_key, 48 символов) и внешний идентификатор сотрудника external_id (например emp-001); при первом ответе запись сотрудника в базе создаётся автоматически;

— нормализация ответов: значения шкал сохраняются с числовым полем score, все ответы привязаны к дате check_in_date для последующей агрегации по периодам;

— изоляция данных организаций (multi-tenant): каждая запись содержит company_id, данные одной компании логически недоступны другой.

3.1.3. Текстовые комментарии

Четвёртый вопрос опроса обеспечивает качественный контекст к количественным показателям. В проекте комментарии хранятся в таблице survey_answers в поле answer наравне с остальными типами ответов. При построении дашборда и сжатого JSON для LLM в приоритете используются числовые агрегаты: среднее настроение, средний стресс, доля положительных ответов о поддержке команды. Полный текст комментариев может передаваться в LLM при базовом анализе wellbeing в режиме полного экспорта; для глубокого анализа в модель направляется сжатая матрица без сырых массивов check-in.

В перспективе развития предусматривается выделение подмодуля анализа тональности (sentiment analysis) текстовых комментариев средствами NLP или LLM без изменения пользовательского сценария в расширении.

3.1.4. Дополнительные источники данных (KPI)

Для сопоставления самочувствия с рабочей нагрузкой в контур анализа включаются внешние системы учёта задач (трекеры). Метрики delivery (созданные, закрытые, просроченные задачи и др.) не являются эмоциональными сигналами, но используются на этапе глубокого анализа совместно с wellbeing (см. п. 3.2 и 3.4).


3.2. Общая архитектура системы

3.2.1. Уровни и потоки данных

Архитектура MVP построена по трёхуровневой схеме.

Клиентский уровень:
— браузерное расширение (сбор check-in, отправка на API);
— веб-дашборд для HR, администратора и руководителя (просмотр аналитики, интеграции, запуск рекомендаций).

Прикладной уровень (монолит Laravel):
— REST API v1 для расширения;
— модули предметной области (сбор, анализ, хранение, интеграция KPI, выявление закономерностей, оценка рисков, рекомендации, панель мониторинга);
— фоновые задачи и планировщик.

Уровень данных и внешние сервисы:
— PostgreSQL — основное хранилище;
— Redis — кэш аналитики, сессии, очереди;
— API трекеров задач (Jira и аналоги);
— API большой языковой модели (в реализации — Gemini через OpenAI-совместимый интерфейс).

Схема взаимодействия (рисунок 3.1 — обобщённая архитектура):

    [Расширение Chrome] ----HTTPS/JSON----> [Nginx -> Laravel API]
                                                    |
    [Веб-дашборд] ------сессия Sanctum-------->  [Модули приложения]
                                                    |
                    +-------------------------------+----------------+
                    v                               v                v
              [PostgreSQL]                      [Redis]      [Jira / LLM API]

3.2.2. Описание основных компонентов

Модуль сбора данных. Назначение — приём и валидация check-in от расширения, определение компании по secret_key, создание или обновление профиля сотрудника, запись ответов в БД. В реализации: CheckInService, эндпоинт POST /api/v1/extension/check-in, клиентское расширение Chrome.

Модуль анализа эмоций. Назначение — расчёт средних показателей, трендов по дням, сводок по отделам и сотрудникам на основе survey_answers. В реализации: AnalyticsService, слой AnalyticsRepository, AnswerScoreCalculator.

Модуль хранения данных. Назначение — персистентное хранение сущностей wellbeing и интеграций, снимков KPI за период, шифрование учётных данных внешних систем. В реализации: PostgreSQL, Eloquent-модели, таблица work_progress_snapshots, шифрование поля credentials в company_integrations.

Модуль интеграции KPI. Назначение — синхронизация метрик задач из трекеров, агрегация по исполнителю (assignee), сопоставление с сотрудником платформы. В реализации: IntegrationManager, коннекторы (JiraCloudConnector и др.), WorkProgressAggregator, IntegrationEmployeeMatcher (точное совпадение email).

Модуль выявления закономерностей. Назначение — объединение wellbeing и KPI в единой структуре «сотрудник — самочувствие — задачи» для экспертного и автоматического анализа. В реализации: DeepAnalysisEmployeeMatrixBuilder, структура employee_delivery_matrix.

Модуль прогнозирования рисков. Назначение — оперативная оценка риска выгорания по правилам и динамике настроения без обращения к LLM. В реализации: BurnoutRiskService, перечисление BurnoutRiskLevel (low, medium, high).

Рекомендательная система. Назначение — генерация текстовых рекомендаций для HR и руководителей по ролевым сценариям (промптам). В реализации: LlmAnalysisService, конфигурационные каталоги analysis_prompts и deep_analysis_prompts.

Панель мониторинга. Назначение — визуализация метрик, управление интеграциями, запуск синхронизации и анализа. В реализации: страницы Blade /dashboard, /dashboard/analysis, /dashboard/deep-analysis, /dashboard/integrations.

3.2.3. Инфраструктура и безопасность

Развёртывание — Docker Compose: nginx, PHP-FPM, PostgreSQL 16, Redis, воркер очереди, планировщик. Фоновая обработка: ProcessCheckInAnalyticsJob после check-in, GenerateWeeklySummaryJob по расписанию.

Безопасность MVP:
— разграничение доступа к дашборду по аутентификации пользователя и привязке к компании (middleware, таблица company_user, роли admin, hr, manager);
— доступ API расширения только при валидном secret_key;
— изоляция tenant по company_id во всех запросах к данным.


3.3. Логическая модель данных

3.3.1. ER-модель (рисунок 3.2)

Логическая модель данных реализована в PostgreSQL. Ниже перечислены основные сущности и связи (обозначения: PK — первичный ключ, FK — внешний ключ, UK — уникальное ограничение).

Сущность companies (организация-клиент): id PK, name, secret_key UK.

Сущность users (пользователь дашборда): id PK, email UK, password, company_id FK (legacy).

Связующая сущность company_user: user_id PK/FK, company_id PK/FK, role — доступ пользователя к одной или нескольким компаниям.

Сущность departments: id PK, company_id FK, name, external_id — отделы внутри компании.

Сущность employees: id PK, company_id FK, department_id FK, external_id, email, name — участники микроопросов.

Сущность surveys: id PK, company_id FK (nullable для глобального опроса), title, is_active.

Сущность survey_questions: id PK, survey_id FK, question, type (scale, boolean, text), sort_order.

Сущность survey_answers: id PK, company_id FK, employee_id FK, survey_question_id FK, answer, score, check_in_date — фактические эмоциональные сигналы.

Сущность integration_providers: id PK, slug UK, name, auth_type — справочник провайдеров (Jira, Linear и т.д.).

Сущность company_integrations: id PK, company_id FK, provider_slug FK, status, credentials (шифровано), settings (JSON).

Сущность employee_integration_identities: id PK, employee_id FK, company_integration_id FK, external_user_id, external_email — явный маппинг с пользователем трекера.

Сущность work_progress_snapshots: id PK, company_id FK, provider_slug, period_from, period_to, payload (JSON), fetched_at — снимок KPI за период; уникальность по (company_id, provider_slug, period_from, period_to).

Основные связи «один ко многим»:
— companies → departments, employees, survey_answers, surveys, company_integrations, work_progress_snapshots;
— departments → employees;
— employees → survey_answers;
— surveys → survey_questions → survey_answers;
— integration_providers → company_integrations → employee_integration_identities;
— employees → employee_integration_identities;
— users и companies связаны через company_user (многие ко многим).

Риск-профиль и текст рекомендаций в базе данных не хранятся: риск вычисляется при запросе аналитики, рекомендации генерируются LLM и возвращаются в ответе HTTP без сохранения (в перспективе — отдельные таблицы risk_profiles и recommendations).

3.3.2. Основные логические сущности предметной области

Пользователи. Различаются два типа субъектов: User (HR, администратор, менеджер — вход на веб-портал) и Employee (сотрудник — только идентификатор в расширении, без пароля на платформе). Company выступает корневым объектом tenant.

Эмоциональные сигналы. Логически представляют собой совокупность ответов check-in за период; физически — набор строк survey_answers с привязкой к типу вопроса. Производные показатели: avg_mood, avg_stress, team_support_yes_rate, тренд настроения по дням.

KPI. Логическая сущность «метрики работы сотрудника за период» материализуется в JSON-снимке work_progress_snapshots.payload, в агрегате work_progress после слияния провайдеров и в строке employee_delivery_matrix.tasks для LLM. Примеры атрибутов: tasks_closed, tasks_created, overdue_count, tasks_open, avg_resolution_days, overdue_issues (список ключей задач).

Риск-профили. Вычисляемая сущность: уровень low / medium / high, текущее и предыдущее среднее настроение, тренд improving / declining / stable. Формируется BurnoutRiskService при обращении к API аналитики.

Предупреждения. Логические сообщения: отсутствие снимка трекера, немаппленные исполнители в Jira, ошибка last_error у интеграции. Отображаются в интерфейсе; отдельная таблица alerts в MVP не предусмотрена.

Рекомендации. Результат работы рекомендательной подсистемы: нумерованный список действий на русском языке. Вход: сжатый JSON (DeepAnalysisLlmPayloadBuilder) и системный промпт выбранной роли.


3.4. Алгоритм обработки данных

Обработка данных в системе организована как последовательный pipeline из восьми этапов (рисунок 3.3).

Этап 1. Сбор данных.
Вход: ответы расширения, запросы к API трекеров при синхронизации.
Обработка: валидация secret_key и вопросов опроса, upsert сотрудника, запись survey_answers; для KPI — запрос задач по JQL (Jira), агрегация, сохранение work_progress_snapshots.
Выход: сырые ответы в БД, снимки KPI за период.

Этап 2. Анализ эмоционального состояния.
Вход: survey_answers за выбранный интервал дат.
Обработка: группировка по сотруднику и дню, расчёт средних и трендов.
Выход: структуры AnalyticsService (обзор компании, история сотрудника), экспорт wellbeing для анализа.

Этап 3. Интеграция с KPI.
Вход: снимки трекеров, справочник employees.
Обработка: маппинг assignee по email, слияние метрик нескольких провайдеров, формирование списка unmapped_assignees.
Выход: агрегат work_progress, предупреждения интеграции.

Этап 4. Выявление закономерностей.
Вход: агрегаты wellbeing и work_progress.
Обработка: построение матрицы employee_delivery_matrix (одна строка на сотрудника: имя, wellbeing-сводка, tasks-метрики).
Выход: матрица для дашборда и LLM.

Этап 5. Сравнение с историческими сценариями.
Вход: показатели текущего и предыдущего периода.
Обработка в MVP: сравнение среднего настроения за последние 7 дней с предыдущими 7 днями (BurnoutRiskService); при глубоком анализе — интерпретация сочетания метрик в промпте LLM.
Выход: тренд настроения; качественное сопоставление «нагрузка — самочувствие» в рекомендациях.

Этап 6. Оценка рисков.
Вход: агрегаты настроения, при deep analysis — KPI из матрицы.
Обработка: пороговые правила → BurnoutRiskLevel; комбинации низкого avg_mood и высокого overdue_count — сигнал для LLM.
Выход: риск-профиль (вычисляемый), флаги для UI.

Этап 7. Генерация предупреждений.
Вход: результаты синхронизации и слияния данных.
Обработка: формирование массива integration_warnings.
Выход: сообщения пользователю в дашборде и в JSON preview.

Этап 8. Генерация рекомендаций.
Вход: сжатый JSON + системный промпт роли.
Обработка: HTTP-запрос к LLM API, нормализация ответа.
Выход: 3–6 пунктов рекомендаций на русском языке.

Два режима конвейера:
— базовый анализ (/dashboard/analysis) — этапы 1–2 и 8 по данным wellbeing (промпты: психолог, HR-аналитик, руководитель);
— глубокий анализ (/dashboard/deep-analysis) — полный цикл с этапами 3–4 и промптами product owner, HR+delivery, team lead.

Оптимизация объёма данных для LLM: перед этапом 8 для глубокого анализа применяется сжатие payload (матрица и сводки без сырых check-in и полных списков задач); число ключей просроченных задач ограничивается параметром конфигурации (по умолчанию 10).


3.5. Механизм формирования риск-профилей

3.5.1. Цель

Механизм риск-профилей предназначен для быстрой количественной оценки вероятности выгорания на дашборде без задержки, связанной с вызовом внешней LLM.

3.5.2. Выявление исторических паттернов

В MVP используется укороченный временной паттерн:
— текущее окно: последние 7 календарных дней, показатель current_average (среднее настроение);
— предыдущее окно: дни с 8-го по 14-й назад, показатель previous_average;
— тренд: при росте среднего не менее чем на 0,2 — improving; при падении не менее чем на 0,2 — declining; иначе — stable.

Правила присвоения уровня риска:
  если current_average < 2,5 — уровень High;
  иначе если current_average < 3,5 и падение относительно previous не менее 0,3 — Medium;
  иначе если current_average < 3,0 — Medium;
  иначе — Low.

Полноценный кластерный анализ или обучение ML-модели на истории компании в текущей версии не применяется; предполагается накопление снимков риска в БД в следующих версиях.

3.5.3. Определение критических значений

Среднее настроение за 7 дней ниже 2,5 — высокий риск.
Среднее настроение ниже 3,0 — средний риск.
Падение настроения к прошлой неделе на 0,3 и более при среднем ниже 3,5 — средний риск как признак ухудшения.
В глубоком анализе: сочетание overdue_count > 0 и низкого avg_mood в матрице — качественный сигнал для HR и для формулировок LLM.

Пороги зафиксированы в модуле BurnoutRiskService и могут быть вынесены в конфигурацию на уровне компании.

3.5.4. Оценка степени сходства сценариев

Целевая проектная модель предполагает библиотеку эталонных сценариев (например «падение настроения при росте просрочек», «высокий стресс при низкой поддержке команды») и метрику сходства текущего состояния с эталоном (правила IF-THEN или расстояние в пространстве признаков).

В MVP формальный scoring сценариев не реализован: интерпретация сочетаний показателей в матрице employee_delivery_matrix возлагается на LLM в рамках промптов глубокого анализа при обязательной опоре на цифры из JSON.


3.6. Механизм формирования рекомендаций

3.6.1. Архитектура

Рекомендательная подсистема построена по схеме «агрегированные данные — промпт роли — LLM — постобработка ответа» (рисунок 3.4).

Последовательность для глубокого анализа:
1) HR выбирает период и провайдеров трекеров на дашборде;
2) DeepAnalysisExportService формирует wellbeing, work_progress и employee_delivery_matrix;
3) DeepAnalysisLlmPayloadBuilder сжимает JSON для отправки в модель;
4) LlmAnalysisService передаёт системный промпт и пользовательское сообщение с JSON в API chat/completions;
5) ответ нормализуется до нумерованного списка на русском и отображается пользователю.

Рекомендации в MVP не сохраняются в базе данных.

3.6.2. Правила формирования рекомендаций

Правила задаются совокупностью системного промпта выбранной роли и общих ограничений в config/llm.php:

— формат ответа: только нумерованный список из 3–6 пунктов на русском языке;
— каждый пункт — одно законченное предложение;
— запрет на выдумывание метрик, не содержащихся во входном JSON;
— для глубокого анализа: в каждой рекомендации указать сотрудника, цифры из tasks и/или wellbeing, при наличии — ключи просроченных задач из overdue_issues;
— запрет markdown, вступлений, постановки медицинских диагнозов.

Постобработка выполняется методом normalizeRecommendation сервиса LlmAnalysisService (удаление разметки, унификация нумерации).

3.6.3. Категории рекомендаций

Категории определяются каталогами промптов, а не отдельной таблицей в БД.

Каталог analysis_prompts (базовый анализ, только wellbeing):
— психолог — моральный климат, стресс, выгорание;
— HR-аналитик — текучесть, вовлечённость, команды;
— руководитель — управленческие действия по состоянию команды.

Каталог deep_analysis_prompts (wellbeing + KPI):
— владелец продукта / delivery manager — риски срыва сроков, перегруз;
— HR + delivery — перегрузка, просрочки, wellbeing;
— тимлид — поддержка конкретных сотрудников, перераспределение нагрузки.

3.6.4. Приоритизация действий

В MVP приоритизация реализована неявно:
— порядок пунктов в ответе LLM (в промпте задаётся акцент на срочные 1:1, top-3 действий);
— визуальный приоритет на дашборде через уровень BurnoutRiskLevel::High до обращения к LLM.

В перспективе: явное поле priority (critical, high, medium) и сортировка рекомендаций по функции scoring от риска, просрочек и тренда.

3.6.5. Ограничения и отказоустойчивость

При недоступности API LLM (код 503, лимиты провайдера) пользователю возвращается сообщение об ошибке; повторный запрос выполняется вручную. На эндпоинты recommend установлено ограничение частоты (throttle). Тарифные лимиты на глубокий анализ заложены в PlanLimitService и подлежат полному внедрению в продуктовой версии.


Заключение по главе

В третьей главе представлено проектирование платформы Wellbeing Monitor: концепция сбора эмоциональных сигналов через микроопросы, модульная архитектура с интеграцией KPI из трекеров задач, логическая модель данных PostgreSQL, восьмиэтапный алгоритм обработки данных, пороговый механизм риск-профилей и рекомендательная подсистема на базе LLM. Проектные решения обеспечивают согласованность с реализуемым MVP и задают основу для развития (тональность текста, хранение истории рисков и рекомендаций, формальная библиотека сценариев). Детали программной реализации компонентов изложены в главе 4.
